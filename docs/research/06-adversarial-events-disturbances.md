## 0. Executive summary

1. The single most important design object is the **reaction budget** `B = (d_spawn - d_min0) / v_c`: the wall-clock time an event leaves a reactor before avoidance becomes physically impossible. With constant velocity during the latency window it is exact (verified by bisection, section 3.4). Scenarios are generated by **choosing B first, then deriving the spawn distance** `d = d_min0 + v_c * B`. Feasibility is then true by construction and is additionally **certified by replaying a zero-latency oracle in the real simulator** (rejection sampling).
2. A reactor with effective latency `L_eff` avoids the event iff `L_eff <= B` (to first order). Hence **collision-rate-vs-latency is the CDF of the budget distribution** you chose. Sampling `B` log-uniformly over 10 ms..5 s makes the latency-sweep curve a clean, interpretable sigmoid-in-log-latency, and lets you separate "fast" from "smart" (section 4).
3. Latency has a physical **knee**: stopping distance never falls below `v*tau_a + v^2/(2a)` (tau_a = attitude/accel lag). With `tau_a ~ 80 ms` and a 30 Hz control tick, shaving decision latency below ~50-100 ms buys almost nothing for the tiny Crazyflie model. Report it, do not hide it.
4. The gym-pybullet-drones CF2X is tiny (27 g, T/W 2.25, [V]); `VelocityAviary` in the source I fetched caps speed at 0.03 * 30 km/h = **0.25 m/s** [V], which makes every event trivially avoidable. Experiments must raise the cap (I recommend `v_cap` = 2 m/s, closing speeds 1..5 m/s) and re-calibrate `a_brake` and `tau_a` empirically in the sim.
5. All randomness must be **counter/channel-keyed** (Philox streams pre-generated per channel), never "next draw from a shared RNG", otherwise arms that consume different numbers of draws see different worlds and the paired design breaks.

## 2. Event models (physics, PyBullet implementation, scheduling, feasibility)

### 2.0 Shared infrastructure

**Keyed, arm-independent randomness.** Every stochastic channel gets its own Philox stream; time series are pre-generated at load time so they do not depend on the controller.

```python
import numpy as np
from numpy.random import Generator, Philox, SeedSequence


def channel_rng(master_seed: int, scenario_idx: int, channel: str) -> Generator:
    # stable string -> int key (do NOT use hash(): salted per process)
    key = int.from_bytes(channel.encode().ljust(8, b"\0")[:8], "little")
    ss = SeedSequence([master_seed, scenario_idx, key])
    return Generator(Philox(ss))


def pregen_normals(rng: Generator, n_steps: int, dim: int) -> np.ndarray:
    return rng.standard_normal((n_steps, dim)).astype(
        np.float32
    )  # 14_400 x 3 floats for 60 s @ 240 Hz = 170 kB
```

**Event clock.** Event onset is expressed either as a sim time (`t_s`, wind, battery, GPS, sensor noise, target motion) or as a **range trigger** (obstacle / second drone: spawn when the drone is within `d_spawn` of a world-fixed spawn point). Range triggers keep the world identical across arms (paired design) while spawn distance -- hence the feasibility guarantee -- holds for every arm (section 4.5).

**Application order per physics step** (one place, deterministic): (1) update event state from the pre-generated arrays by step index `k`; (2) apply external forces (wind, battery-scaled rpm); (3) `p.stepSimulation()`; (4) contact/clearance check; (5) sensor corruption applied only to the *observation* path, never to physics.

### 2.1 Sudden obstacle

**Model.** A sphere (radius `R_o`, 0.10-0.30 m) or box that becomes a collision body at `t_spawn`, on a *collision course* with the drone's current path:

`p_obs = p_drone + d * u_v + delta * u_perp`, with `|delta| < R_hit_eff`, `R_hit = R_o + r_d` (r_d = 0.06 m drone radius, [V] URDF), `u_v` = unit of the **planned/nominal** velocity.

Variants: (a) static pop-up; (b) crossing obstacle with velocity `v_o` (closing speed uses `v_c = v_drone * cos + v_o * cos`); (c) dropped object from above (vertical closing `v_c = sqrt(2 g h)` for free fall; caps at ~5 m/s for h=1.3 m); (d) **decoy** (`|delta| > R_hit + margin`: no action needed -- tests over-reaction, and gives the label "CONTINUE").

**PyBullet.**

```python
import pybullet as p


def make_obstacle_pool(client, n=4, radius=0.2):
    col = p.createCollisionShape(p.GEOM_SPHERE, radius=radius, physicsClientId=client)
    vis = p.createVisualShape(
        p.GEOM_SPHERE, radius=radius, rgbaColor=[1, 0, 0, 1], physicsClientId=client
    )
    # mass=0 => kinematic/static; parked far away so it does not exist for sensors or contacts
    return [
        p.createMultiBody(
            0, col, vis, basePosition=[1e3, 1e3, -1e3 - i], physicsClientId=client
        )
        for i in range(n)
    ]


def spawn(
    obs_id, pos, client
):  # "appears": teleport from parking spot (O(1), no body churn, stable ids)
    p.resetBasePositionAndOrientation(obs_id, pos, [0, 0, 0, 1], physicsClientId=client)


def move_kinematic(
    obs_id, pos_k, client
):  # moving obstacle: reset every physics step from a precomputed path
    p.resetBasePositionAndOrientation(
        obs_id, pos_k, [0, 0, 0, 1], physicsClientId=client
    )


def min_clearance(drone_id, obs_id, client, max_d=3.0):
    pts = p.getClosestPoints(drone_id, obs_id, distance=max_d, physicsClientId=client)
    return min((c[8] for c in pts), default=max_d)  # contactDistance; <0 => penetration


def collided(drone_id, obs_id, client):
    return len(p.getContactPoints(drone_id, obs_id, physicsClientId=client)) > 0
```

Pre-created/parked bodies are preferable to creating bodies mid-episode (stable body ids, no allocator churn, determinism). Parked bodies must be excluded from raycasts -- keep them >1e3 m away ([I]; sensor range 4-10 m). `getClosestPoints`'s field 8 is `contactDistance` [U] verify in 02's spike. Near-miss = `min_clearance < 0.15 m` (tunable, agent 08 defines).

**Scheduling.** Number of obstacle events per flight `~ Poisson(lambda*T)` truncated to [0,3], inter-event gap `>= T_min_gap = 4 s` (prevents overlapping events, which would break the per-event budget guarantee), onset uniform in `[t_warmup, T - t_tail]`, `t_warmup = 3 s`. Severity = tier of B (section 4), `R_o`, `v_c`.

### 2.2 Wind changes / gusts

**Model.** Total wind `w(t) = w_mean(t) + w_turb(t)`; force on the drone `F_w = 0.5 rho Cd A |w - v| (w - v)` (relative airspeed, so the drone's own speed damps it).

- **Mean wind step** (the "wind changes" event): `w_mean` jumps from `w0` to `w1` at `t_s` with a first-order ramp `tau_ramp` 0.5-2 s. Magnitude `|w1 - w0|` in 1..5.4 m/s, direction uniform.
- **Turbulence, Dryden (MIL-F-8785C / MIL-HDBK-1797)**. Low-altitude scale lengths `L_w = h`, `L_u = 2 L_v = h / (0.177 + 0.000823 h)^1.2` (h in feet), `sigma_u = sigma_v = sigma_w / (0.177 + 0.000823 h)^0.4` [V] (https://arxiv.org/pdf/1905.09954 and MathWorks Aerospace Blockset Dryden docs, accessed 2026-09-30). The textbook constants `sigma_u = sigma_v = 2.12 m/s, sigma_w = 1.4 m/s, L_u = L_v = 200 m, L_w = 50 m` are the MIL-F-8785C medium/high-altitude values [V] (same search). Transfer functions (MIL-HDBK-1797): `H_u(s) = sigma_u sqrt(2 L_u/(pi V)) / (1 + (L_u/V) s)`, `H_w(s) = sigma_w sqrt(L_w/(pi V)) (1 + sqrt(3)(L_w/V)s) / (1 + (L_w/V)s)^2` [I from memory of the handbook; confidence Med -- re-check against MathWorks page before coding]. `sigma_w = 0.1 * W20` (W20 = wind at 20 ft; light 15 kt, moderate 30 kt, severe 45 kt) [I/Med].
- **Problem for a hover-speed micro-UAV**: Dryden is parameterised by airspeed `V` and breaks at `V -> 0`. The Dryden model was derived for large aircraft but has been applied to small UAVs at low altitude [V] (arXiv 1905.09954). **Recommendation: use an Ornstein-Uhlenbeck (OU) gust per axis as the primary turbulence model**, with `tau = L / max(V, V_min)` and `V_min = 1.0 m/s`, stationary std `sigma`:

  `dw = -(w/tau) dt + sigma*sqrt(2/tau) dW`, exact discretisation `w_{k+1} = e^{-dt/tau} w_k + sigma sqrt(1 - e^{-2 dt/tau}) N(0,1)`.

  Parameter ranges ([I], scaled for a 27 g drone at h = 1-3 m = 3-10 ft, where `sigma_u/sigma_w = 1/(0.177+0.000823 h)^0.4 ~ 1.98-1.95`): `sigma_w in {0.1, 0.3, 0.6, 1.0} m/s`, `sigma_u = sigma_v ~ 2 sigma_w`, `tau in [0.3, 3] s` (L = 1-3 m / V_min 1). Vertical gust `sigma_z ~ 0.5 sigma_xy`.
- **Discrete gust** ("1-cosine", MIL-F-8785C / FAR 25.341 style): `w(t) = (w_g/2)(1 - cos(pi t / T_g))`, `T_g` 0.3-1.5 s, `w_g` 1-4 m/s; tests a sharp transient rather than a statistical process. [I/Med]

**PyBullet.** Forces are cleared after every `stepSimulation`, so apply each physics step. gym-pybullet-drones' own `PYB_DRAG` mode does not model ambient wind. Inject via `applyExternalForce`:

```python
def apply_wind(client, drone_id, v_world, wind_world, rho=1.225, cd=1.0, area=0.003):
    v_rel = np.asarray(wind_world) - np.asarray(
        v_world
    )  # air velocity relative to body
    f = 0.5 * rho * cd * area * np.linalg.norm(v_rel) * v_rel  # N, world frame
    p.applyExternalForce(
        drone_id, -1, f.tolist(), [0, 0, 0], p.WORLD_FRAME, physicsClientId=client
    )
```

Where to call it inside gym-pybullet-drones: override `_physics(self, rpm, nth_drone)` (called once per pybullet step in `BaseAviary.step`, then `p.stepSimulation()`) -- call `super()._physics(...)` then `apply_wind(...)` [U: verify hook ordering in the installed version; 02 owns]. If the aggregation loop differs, override `step`'s inner loop instead. Wind needs the current drone world velocity `p.getBaseVelocity`.

**Scheduling.** Mean-wind steps: Poisson with rate 1/20 s, minimum gap 6 s; turbulence always on at the scenario's `sigma` level (constant across the flight, a difficulty knob, not an "event"). Curriculum: sigma level 0 -> 1 over tiers.

**Feasibility.** Require (i) `a_w,max = 0.068*(|w_mean| + 3 sigma)^2 <= 0.5 a_brake` (this is a sanity cap; it guarantees the drone keeps >= 50% of its decel authority); (ii) during the obstacle budget computation use the *effective* decel `a_eff = a_brake - a_w,head` for the worst-case axis where `a_w,head = 0.068 w_par^2` is the tail-wind component against braking (tail wind pushes the drone forward). This is conservative and makes wind x obstacle events jointly feasible.

**Correct action** (section 6): wind steps themselves rarely have a *discrete* correct action -- the controller absorbs them. Correct label = CONTINUE (mission action) unless cross-track error > threshold and approaching an obstacle/geofence (then BRAKE/HOVER), or sustained headwind makes `E_return` violate battery reserve (RETURN_HOME). This is an important finding: **wind is mostly a confound/stressor that shrinks margins, and an over-reaction trap**, not a discrete-action event.

### 2.3 Target moves

**Model.** Waypoint target position `x_T(t)`, four variants: (a) **jump** (teleport by `Delta` with `|Delta| in [1, 4] m`) at `t_s`; (b) constant velocity `v_T in [0.1, 0.6] v_cap`; (c) OU-heading random walk `theta' = -(theta - theta_0)/tau + sigma_th dW`, speed const; (d) evasive (flees drone): restricted to `v_T <= 0.6 v_cap`.

**PyBullet.** Purely kinematic: target is a visual marker via `p.resetBasePositionAndOrientation` of a mass-0 body with no collision shape (`createVisualShape` only, `collisionFilterGroupMask` not needed). The `Observation` exposes the relative target vector, noisy per section 2.4.

**Feasibility.** Capture is feasible iff `v_T < v_cap` for pursuit (sustained) and for jumps `|Delta| / v_cap + T_turn <= T_deadline` where `T_turn ~ pi/omega_yaw + tau_v` (<= 1 s). The generator sets `T_deadline` per tier (e.g. 2.0 s for "reach target within X").

**Correct action:** turn toward bearing: LEFT/RIGHT by sign of relative bearing above 10 deg dead-band; ASCEND/DESCEND by elevation; FORWARD when `|bearing| < 10 deg`.

### 2.4 Sensor noise / dropout

Applied to the **observation path only** (physics unaffected).

Per-channel model for channel `y` (position, velocity, relative target, ranges):

`y_meas(k) = y_true(k) + b(k) + n(k)`, with
- white noise `n ~ N(0, sigma^2)` ([I] ranges: position sigma 0.02..0.5 m, velocity 0.02..0.3 m/s, range sensor `sigma_r = sigma_0 + k_r * r` with sigma_0 = 0.01..0.05 m and k_r = 0.005..0.03 (proportional to range, typical of ToF/ultrasonic));
- bias random walk `b(k+1) = b(k) + sigma_b sqrt(dt) N`, `sigma_b` 0.005..0.05 m/sqrt(s);
- **dropout** as a 2-state Gilbert-Elliott chain with `P(good->bad) = p_gb`, `P(bad->good) = p_bg`; in `bad` the channel returns either last value (stale hold, *silent*) or NaN (flagged). Burst length mean `1/p_bg` = 50-500 ms. Steady-state loss `p_gb/(p_gb+p_bg)` in 1..30%;
- **range-specific**: missed detection `p_miss` 0-0.3 per ray, ghost return `p_ghost` 0-0.02 (random short range), quantisation 1 cm;
- **sensor latency** 0-100 ms (FIFO delay in observation buffer; distinct from decision latency; agent 08 owns accounting).

**Feasibility.** Noise does not alter physics, but shrinks the effective detection budget. Rule: the generator inflates `d_min0` by detection margin `3 sigma_r(d) + v_c * T_confirm`, with `T_confirm` = 1..3 sensor frames of consistent detection a sensible perception stack needs. Dropout bursts: events (obstacle spawn) are never scheduled when dropout is in a burst at `t_spawn - T_pre`; or more simply, a reactor is assumed to see the obstacle at `t_spawn + t_det`, where `t_det` = time until the first non-dropped frame, and `t_det` is **computed from the stored dropout array** and subtracted from B (`B_eff = B - t_det`). Keep `t_det <= 0.25 B` by resampling (rejection).

**Correct action:** noise is a stressor; label = the action implied by the *true* state (e.g. BRAKE for a real obstacle, CONTINUE on a noise-induced ghost). Ghost returns are a false-alarm trap: the label is CONTINUE while `ghost` flag set in ground-truth metadata.

### 2.5 Battery drop

**Model** (1S LiPo, CF2-class 240 mAh [I]). Terminal voltage `V = V_oc(SOC) - I R_int`; `V_oc` 4.2 V (full) -> 3.3 V (empty) [V, cell range 4.2 -> 3.2 V from search: arXiv 2302.07208 style statements, accessed 2026-09-30]. Thrust at fixed duty scales `T ~ omega^2 ~ V^2` (the thrust reduces quadratically with the voltage drop [V] same source), so **derating factor `k_T = (V / V_ref)^2`**, with `V_ref` the voltage at which the PID hover trim was tuned. Hover current `I_h ~ P_h / V`; `P_h = (m g)^{3/2} / sqrt(2 rho A_rot_total)` ideal momentum theory [I, ~ 2.5-3 W at 27 g, agrees with ~7 min flight on 240 mAh]. SOC dynamics `dSOC/dt = -I/(3600 Q)`.

Battery "drop" event = step change, either (a) **SOC step** `Delta_SOC` in 10..40% (cell failure/brownout), (b) **resistance jump** `R_int` x 2..4 (cold pack/ageing) producing larger sag under thrust bursts, or (c) accelerated drain rate x 2..5.

**PyBullet.** Scale thrust by scaling the commanded rpm before physics (rpm ~ V for a fixed-duty motor, so force ~ V^2 comes for free):

```python
def battery_scale_rpm(rpm_cmd, v_term, v_ref, max_rpm):
    return np.minimum(
        rpm_cmd * (v_term / v_ref), max_rpm
    )  # force = kf * rpm^2  -> (V/Vref)^2
```

Hook in the same `_physics` override. `v_term` is computed from SOC and the current `I ~ sum(kf*rpm^2)`-derived power. Because the PID hover trim is fixed at nominal, the drone *sags* as k_T falls (realistic: real firmware compensates with voltage compensation; expose `voltage_comp: bool` as a scenario flag).

**Feasibility.** Keep `k_T * (T/W) >= 1.25` at all times until emergency-land state (so a_brake stays >= 2.5 m/s^2); when an obstacle event is scheduled after a battery event, the generator recomputes `a_eff` with derated thrust: `a_eff = g*sqrt((k_T * 2.25)^2 - 1) * (4/5.66)` [I]. Return feasibility: `E_return = P_cruise * d_home / v_cruise`; a scenario is "RETURN feasible" iff `SOC_after * Q * V_nom >= E_return * (1 + 0.2)`; else the only correct action is EMERGENCY_LAND (and the scenario is tagged `no_return`).

**Correct action.** `SOC > SOC_return_req(d_home)`: CONTINUE. `SOC_land_req < SOC <= SOC_return_req`: RETURN_HOME. `SOC <= SOC_land_req` or return infeasible: EMERGENCY_LAND. (`SOC_land_req` = energy to descend from current altitude at `v_descent = 1 m/s` plus 10% reserve.)

### 2.6 GPS disappears

**Model.** Position channel `p_gps = p_true + b_g(t) + n_g`, `b_g` Gauss-Markov `b' = -b/tau_g + sigma_g sqrt(2/tau_g) dW` with `sigma_g` 0.5-3 m, `tau_g` 60-300 s [I, consumer GPS ranges]. Failure modes: (a) **dropout** (no fix: flagged or frozen silently); (b) **slow drift/spoof**: bias ramps `b(t) = r (t - t_s) u` with `r` 0.05-0.5 m/s until `b_max` 5-20 m; (c) **jump** (multipath) 3-10 m step. After loss, dead-reckoned estimate error grows `sigma_p(t) = sigma_0 + k_v * v_avg * t + 0.5 k_a t^2` with `k_v ~ 0.02-0.1` (velocity-estimate error fraction) [I/Low].

In the simulator ground truth is free; the "GPS" is a *modelled sensor*, so the drone controller must be fed the corrupted estimate (PID takes position from `estimate`, not `true_state`) for the loss to matter physically; otherwise GPS loss is cosmetic. **Design decision: add an `EstimatorStub` between truth and the PID state input** (truth + bias + noise during GPS ok; velocity-integrated dead-reckoning with growing error after loss). Low confidence this is worth the complexity for the first version; minimum viable version = GPS-loss only affects what Jev *observes* (`gps_valid`, `position_error_estimate`) and the correct action is a policy label, physics unchanged.

**Feasibility.** GPS loss is survivable iff (i) altitude/attitude remain observable (baro/flow, assumed always available), (ii) a non-GPS safe action exists (HOVER/EMERGENCY_LAND). Generator constraint: no obstacle event within `T_gps_guard = 3 s` of loss unless obstacle avoidance is body-frame (range sensors, unaffected). Drift scenarios bound `b_max` so that `b_max < geofence_margin` for the return leg.

**Correct action:** loss flagged -> HOVER immediately (hold, `T_hold <= 3 s`), then RETURN_HOME if `sigma_p(t) < 0.5 * d_home_clearance` else EMERGENCY_LAND. Silent-drift (unflagged): ideal = detect inconsistency (estimate vs optical-flow velocity), label HOVER then EMERGENCY_LAND; scored as "detection-delay" metric.

### 2.7 Another drone enters trajectory

**Model.** Intruder (second CF2X or a kinematic sphere of radius `r_i = 0.06 m`) with policies, in increasing adversarial strength:

1. **Scripted constant-velocity crossing** on a collision course: constant bearing decreasing range (CBDR). Geometry: choose time-to-collision `t_c`, place the intruder at `p_i(t_spawn) = p_hit - v_i t_c` where `p_hit = p_d + v_d t_c`. Relative closing speed `v_c = |v_d - v_i| ` projected on the line of sight.
2. **Head-on** (v_i antiparallel).
3. **Cooperative (ORCA/VO) intruder**: intruder reacts; used as a non-adversarial "interaction" test.
4. **Adversarial mirror**: intruder replicates the drone's lateral offset with limited accel `a_i <= 0.5 a_d`. Excluded from feasibility certificates (unbounded adversary); reported as a separate `stress` class.

**PyBullet.** Simplest: kinematic sphere moved by `resetBasePositionAndOrientation` (section 2.1), which costs nothing. Full second CF2X (2-drone `CtrlAviary`) costs roughly a second drone's physics (+ a second PID) per step and is warranted only for policy-4 or aerodynamic (downwash) studies [I]. Recommend: kinematic intruder in v1, real drone in a later phase.

**Feasibility.** Same as 2.1 with `v_c = |v_rel| cos(angle_LOS)`, `R_hit = 2 r_d + margin`, and `a` decel of the ego only (intruder is non-adaptive after spawn in tiers 1-2). For scripted intruders we additionally require that intruder `t_commit` (time after which its path is fixed) precede spawn: its path is fixed at spawn, so avoidability by lateral shift is well defined. Require `v_i <= v_cap`.

**Correct action:** AVOID_LEFT/RIGHT toward the side with greater predicted miss distance (away from intruder lateral velocity) if `d_swerve <= d`; BRAKE if `d_brake <= d` and swerve would exit geofence or conflict with a second obstacle; both when feasible -> prefer the one that (by rollout) maintains progress (section 6).

## 3. Feasibility and avoidability math

### 3.1 Setting

The "perfect zero-latency reactor" is the best any controller could possibly do given the drone's physical limits and the *discrete* actuation pipeline. Model (point mass, the simplest model that captures the knee):

- closing speed along the line of sight `v_c >= 0` (obstacle static: `v_c = |v_drone|`);
- commanded accel saturates at `a` (brake) and `a_lat` (lateral), both `<= g tan(theta_max)`;
- accel tracks command through a first-order lag `tau_a` (attitude loop + velocity loop), `da/dt = (a_cmd - a)/tau_a`;
- reactor latency `L` = time between obstacle *appearing* (becoming visible) and the commanded acceleration *starting*;
- collision radius `R_hit = R_o + r_d` (+ safety margin `m_s` for "clear", default 0.15 m).

### 3.2 Two escape manoeuvres

**(A) Brake to a stop before contact.** During latency the drone coasts at `v_c`; afterwards `a(t) = a (1 - e^{-(t-L)/tau_a})`. Stopping distance:

`s_stop(v_c, L) = v_c L + s_brake(v_c)`, with `s_brake` = distance until `v = 0` under the lagged profile. Closed-form upper bound (conservative, since the lag loses at most `a*tau_a` of velocity change):

`s_brake <= v_c * tau_a + v_c^2 / (2a)`.

Spawn-range requirement: `d >= R_hit + v_c L + s_brake(v_c)`.

**(B) Swerve laterally** by at least `w = R_hit + m_s` (in obstacle-lateral coordinates) before the range closes to `R_hit`. Lateral displacement under lagged step accel: `y(t) ~ 0.5 a_lat (t - tau_a)^2` for `t >> tau_a` (exactly simulated in the script). Time to shift `t_s(w) ~ sqrt(2w/a_lat) + tau_a`-ish; range requirement:

`d >= R_hit + v_c (L + t_s(w))`. Note: no need to stop laterally; clearance is only needed at the crossing instant.

**Minimum spawn distance for a zero-latency reactor**

`d_min0 = R_hit + min( s_brake(v_c) , v_c * t_s(w) )` (L = 0).

For `v_c` below the crossover (`~4.2 m/s` at a=4, tau=0.08, w=0.46) BRAKE is cheaper (quadratic term small); above it SWERVE is cheaper. The feasible set has two disjoint-dimension modes, hence the action set must contain both BRAKE and AVOID_*.

### 3.3 Reaction budget

Define the **reaction budget**

`B(d, v_c) = (d - d_min0(v_c)) / v_c`     [seconds]

= the maximum total latency (sense age + inference + network + wait for next decision tick + actuation-start delay) a reactor can incur and still avoid the event using the better of the two manoeuvres. Because velocity is constant during `L`, `d_min(L) = d_min0 + v_c L` is **exactly** linear in `L`.

Generalisation with tail wind `a_w` and battery derating: replace `a` by `a_eff` (2.2, 2.5). With sensor detection delay `t_det`: `B_eff = B - t_det`.

Also define per-manoeuvre budgets `B_brake`, `B_swerve`; `B = max(B_brake, B_swerve)` for a scenario that admits both, and a scenario tagged `swerve_only` if `B_brake < 0 <= B_swerve` (used to test that AVOID actions are chosen when BRAKE fails).

### 3.5 Effective latency and what a reactor is compared against

`L_eff = t_obs_age + t_infer + t_net + t_wait_tick + t_act_start`, where `t_wait_tick ~ U(0, T_dec)` for a fixed decision period `T_dec` (mean `T_dec/2`, worst `T_dec`), `t_obs_age` = sensor-to-observation staleness (0..1/f_sensor), `t_act_start` ~ one control tick (33 ms at 30 Hz; the lag `tau_a` is already in `s_brake`). Illustrative (script output, worst case / mean, ms; the brake-path tick 4 ms is a placeholder for the 240 Hz physics step):

| Reactor | worst-case `L_eff` | mean `L_eff` |
|---|---|---|
| PID/TTC braking, 30 Hz, 2 ms compute | 39 | 22.5 |
| Jev-like 10 ms model, 50 Hz tick | 34 | 24 |
| Jev-like 50 ms | 104 | 79 |
| Fast LLM 300 ms | 604 | 454 |
| Big LLM 2 s | 4004 | 3004 |

(Agent 08 owns the precise time accounting; agent 01 the latency numbers; this table is illustrative.)

**Mapping to tiers.** A reactor with `L_eff` (sampled per decision) avoids the event iff `L_eff <= B_eff`. Hence `P(collision | L_eff) = P(B_eff < L_eff)` = CDF of the scenario budget distribution (up to execution noise). That equality is what makes the latency sweep interpretable.

**Latency knee** (for agent 13): `d_min(L)` has a floor `d_min0 > 0` dominated by `v tau_a + v^2/2a`; at v=2, L=0 -> 0.95 m; L=50 ms -> 1.05 m; L=1 s -> 2.95 m. Sensitivity `dd/dL = v_c`, so when budgets in the scenario set are all above ~300 ms, reducing `L_eff` from 100 ms to 10 ms changes *nothing* about collisions. The discriminating regime is `B in [L_fast, L_slow]`, which is why the tier set must cover 10 ms..5 s.

### 3.6 Calibration against the real sim (required before trusting the tiers)

`a_brake`, `a_lat`, `tau_a` are **properties of DSLPIDControl + CF2X in gym-pybullet-drones + action mapping**, not free parameters. Procedure (headless, ~1 min):

1. Fly at `v_c` in {0.5, 1, 2, 3, 4} m/s along x with the stock PID velocity mode; at `t0` command `v_des = 0` (BRAKE mapping from agent 11). Record `s_stop_meas(v_c)`.
2. Fit `(a, tau_a)` by least squares of `s_stop = v*tau_a + v^2/(2a)`; same for lateral step (AVOID mapping) `y(t)`.
3. Re-run the generator with fitted values and multiply `a` by `kappa_a = 0.85` (modelling error margin) and add `+0.10 m` to `d_min0`.
4. Also measure `tau_a` dependence on thrust headroom and on `k_T` (battery) -- the lag grows as thrust saturates; `d_min0` must use the worst case over the allowed `k_T, a_w` range.

If the hover PID saturates or diverges at 3+ m/s with stock gains, lower `v_cap` (this is the real limit, not the ranging model) [U/Low: stock DSLPID tuned for gentle flight].

### 3.7 Empirical feasibility certificate (recommended, belt and braces)

For every generated scenario run **Oracle-0**: a scripted reactor with 1-tick latency (L = 1 control tick) that, at the first tick where the obstacle is in sensor range, selects the better of {BRAKE, AVOID_L, AVOID_R} by the analytic rule and then CONTINUE. If it collides or violates the clearance margin, the scenario is **rejected and resampled** (same seed stream advanced by a documented rejection counter; the final accepted counter is stored). Store `certified: {oracle: "oracle0", latency_ticks: 1, min_clearance_m: 0.31}`. Also store an **Oracle-B run at `L = B`** (should sit at the boundary, clearance ~ margin) to validate that the budget formula predicts the real boundary in the simulator; reject/retune the model if `|B_true - B_model| > 0.1 B`. This is cheap (one extra flight per scenario) and converts the analytic guarantee into an empirical one.

## 4. Difficulty tiers and the latency sweep

### 4.1 Tier definition (relative to the reaction budget)

Tiers are defined by the **zero-latency budget B** (not by spawn distance, which depends on speed):

| Tier | Budget B | Who can plausibly pass | Purpose |
|---|---|---|---|
| T0 "relaxed" | >= 3000 ms | everything incl. 2 s LLM | sanity, floor of collision rate ~ 0 |
| T1 "easy" | 1000-3000 ms | >= 500 ms models | |
| T2 "moderate" | 300-1000 ms | <= 300 ms models | LLM/fast-LLM separation |
| T3 "hard" | 100-300 ms | Jev-class (<100 ms), reactive PID | |
| T4 "tight" | 30-100 ms | only < 1-2 ticks reactors (reactive PID/TTC) | knee; physics-limited |
| T5 "edge" | 0-30 ms | oracle-only | boundary test |
| T-1 "impossible" (control) | B < 0 | nobody; expected collision rate 100% | validates physics/collision detection; report but *exclude* from headline rates |

Normalised difficulty for plotting: `rho = L_eff / B` (margin ratio). `rho <= 1` avoidable; `rho = 0.5` comfortable; `rho > 1` should collide. Plot outcome vs `rho` for all arms: if curves collapse onto one sigmoid around `rho = 1`, the model is validated; arm-specific deviations = "smartness" (wrong action, oscillation) rather than speed.

**Sampling.** Headline suite: `B ~ LogUniform(10 ms, 5 s)` (equal mass per decade; 2.7 decades) -> the collision-rate-vs-latency curve is approximately `1 - log(L/10ms)/log(500)` over the range, with a known slope, easy to eyeball. Stratified alternative: equal N per tier (recommended for power: 6 tiers x N). Always include T-1 at 5% as control.

### 4.2 Generator algorithm

```
def make_obstacle_event(rng, v_c, tier, params):
    B = sample_budget(rng, tier)                          # seconds
    a_eff, tau = derated(params, scenario_context)        # battery/wind derating at t_spawn, includes kappa_a
    d_b, d_s, d0 = d_min(v_c, a_eff, a_eff, tau, w, R_hit)
    d_spawn = d0 + v_c * (B + t_det_from_noise_arrays)
    assert d_spawn <= params.sensor_range - params.range_margin   # else resample v_c/B or drop the event
    lateral_offset = rng.uniform(-0.5, 0.5) * R_hit           # collision course; decoys: +-(R_hit+0.3..1.0)
    return Event(type="obstacle", trigger={"kind":"range", "d_spawn": d_spawn, ...}, budget_s=B, tier=tier)
```

**Constraint**: `d_spawn <= R_sense` (sensor can see it at spawn). This couples tiers to closing speed: with `R_sense = 4 m` (assumed Multi-ranger class [U]) and `a = 4`, tier T0/T1 (B >= 1 s) requires `d0 + v_c*1.0 <= 4 -> v_c <= ~2.5`; generate high-speed T3-T5 events; use `v_c` sampled as a function of tier: `v_c ~ U(0.5, v_max(B))`, where `v_max(B) = max{v: d0(v) + vB <= R_sense}` (computed numerically; in the script a 6 m sensor gives 9.8/8.7/6.6/3.7 m/s for B = 30/100/300/1000 ms).

### 4.3 Latency sweep design (for agent 08)

Sweep L in {0, 10, 50, 100, 300, 1000, 3000} ms applied as *delay on the action path* (latency injection, option (c)). Predicted collision fraction for a perfect-policy reactor at each L = `F_B(L)`. For log-uniform B in [10 ms, 5 s]: `F_B(0)=0`, `F(10)=0`, `F(50)=0.26`, `F(100)=0.37`, `F(300)=0.53`, `F(1000)=0.74`, `F(3000)=0.93` (computed from `log(L/10ms)/log(500)`; includes neither execution noise nor T-1). Deviation of any arm from `F_B(L_eff,arm)` isolates policy quality. **Report latency-matched comparisons**: Jev at injected latency equal to the LLM's, to separate speed from smartness.

### 4.4 Ablation design

Factorial with paired scenarios (same seed -> same world):

- Factor A event type {obstacle, intruder, wind, GPS, sensor, battery, target} single-event flights vs combined.
- Factor B severity tier (B for obstacles/intruder; sigma/jump size for others).
- Factor C disturbance stack {none, wind only, wind+noise, wind+noise+battery derating}; tests `a_eff` margin handling.
- Factor D sensor quality {perfect, noisy, noisy+dropout}.
- Factor E decision latency {sweep}.
- Factor F flagged vs silent GPS/sensor faults (does the model detect inconsistency?).

Single-event flights first (clean attribution), then 2-event combos with `T_min_gap >= 4 s` and guarantee that feasibility certificates hold for the *combined* derated state (oracle replay of the whole flight).

### 4.5 Why range-triggered, world-fixed spawns

Arms fly slightly different trajectories. If events were time-triggered relative to the drone they would place obstacles differently per arm; if time-triggered in world coordinates, some arms would be far away when it appears. **Range-triggered world-fixed spawn**: obstacle position fixed in world (from the seed); it appears when `||p_drone - p_spawn_zone|| <= d_spawn`. Every arm therefore faces the same obstacle at the same range; closing speed differs by arm but is upper-bounded by `v_cap` (enforced by the speed clamp for all arms), so `d_min0(v_cap)` is a valid bound and **the feasibility guarantee holds for every arm** (slower arms just get more budget -- report `B_realised = (d - d_min0(v_c,real))/v_c,real` per flight and stratify on it). Caveat: arms with lateral cross-track error may not be on collision course; report `collision_course_at_spawn` (boolean from geometry) and exclude/flag non-collision-course flights from "avoidance" metrics.

## 6. Ground-truth "correct action" labelling

### 6.1 Principle: viability, not imitation

A label is a **set of acceptable actions and a preferred action**, computed by forward-simulating the action through the drone's physical model (point-mass + calibrated `a`, `tau_a`, with the same action-to-setpoint mapping as agent 11) against the **true** world state, *not* a hand-coded if-tree. Hand-coded labels would embed one designer's policy and punish valid alternatives (BRAKE vs AVOID both fine).

For each decision instant `t` and each action `u` in the 11-element set:

1. Apply `u` as the mapping does (latched with its TTL), starting after the **assumed application latency** `L_a` (see 6.3), then continue with the **recovery policy** `pi_rec` (brake/avoid oracle, then mission CONTINUE).
2. Roll out for horizon `H` (2 s default; 1 ms-10 ms steps using the point-mass model, vectorised, ~11 x 200 steps, cheap, no pybullet).
3. `u` is **safe** iff: min clearance to every obstacle/intruder/ground/geofence `>= m_s` (0.15 m), battery reach satisfied, and no hard-constraint violation.
4. `S(t) = {u : safe}`. `deadline(t)` = latest `t'` such that `S(t')` non-empty; `urgency = deadline - t`.
5. **Preferred** action = argmin over `S(t)` of lexicographic cost (1) safety margin shortfall, (2) `dist_to_goal` after H (progress), (3) energy/jerk, (4) action switches. Ties broken deterministically (enum order).

### 6.2 Rule tables per event (sanity constraints on the rollout oracle; used as unit-test expectations)

| Situation | Acceptable / preferred |
|---|---|
| No active hazard | CONTINUE-mission action: FORWARD / LEFT / RIGHT / ASCEND / DESCEND by relative target vector; HOVER only at target |
| Obstacle on course, `d >= d_brake(L)` | BRAKE acceptable; preferred if swerve blocked or geofence tight |
| Obstacle on course, `d >= d_swerve(L)` | AVOID_LEFT/RIGHT acceptable; preferred = side with more free lateral clearance; BRAKE alone not acceptable if `d < d_brake(L)` |
| `d < min(d_brake, d_swerve)` for all L >= L_a | `S = {}` -> label `UNAVOIDABLE`; excluded from accuracy, used in T-1 controls |
| Decoy (miss distance > margin) | CONTINUE-mission acceptable; BRAKE/AVOID marked "unnecessary" (false alarm, not collision) |
| Intruder | as obstacle; AVOID side = away from intruder lateral velocity (passing behind) |
| Wind step, no hazard | mission action; HOVER acceptable only if cross-track error > 0.5 m and growing |
| Sensor ghost | mission action (true state is safe); BRAKE is a false alarm |
| Sensor degraded, real obstacle | as obstacle (true state) |
| GPS loss flagged | HOVER for `T_hold <= 3 s`, then RETURN_HOME if `sigma_p < 0.5 * clearance`, else EMERGENCY_LAND |
| Battery `SOC > SOC_ret` | mission action |
| Battery `SOC_land < SOC <= SOC_ret` | RETURN_HOME (BRAKE/HOVER acceptable for one tick) |
| Battery `SOC <= SOC_land` or return infeasible | EMERGENCY_LAND |
| Target jump | turn toward target (LEFT/RIGHT/ASCEND/DESCEND); HOVER acceptable for <= 0.5 s |

(If the action set proves insufficient, e.g. no speed or yaw actions, see agent 11.)

### 6.3 Which state and latency the label refers to (important for fairness)

Store **two labels** per decision: `label_obs` (computed on the state *as observed* at `t_obs`, what a perfect-perception fast reactor would pick) and `label_apply` (computed on the true state at `t_apply = t_obs + L_eff`, what is physically right by the time the action takes effect). Score:

- **Hard metrics** (collision, clearance): physics, label-free.
- **Decision correctness**: `u in S_apply` = "acceptable"; `u == preferred_apply` = "optimal". Stale decisions judged on the apply-time set capture staleness cost.
- **Reaction time** = `t_first(u in S) - t_event_visible`, evaluated with `urgency`; **regret-to-deadline** = `deadline - t_first_correct` (negative => too late).
- **False alarm rate** on decoys/ghosts, **invalid-output rate**, **oscillation** (switches per s).

Labels are stored as a per-flight compact array `(t, S_bitmask_obs(11 bits), pref_obs, S_bitmask_apply, pref_apply, urgency)` plus the oracle's `recovery_policy_version`; the decision's own `action` is joined at analysis time (`flights` / `decisions` tables of agent 10). Labels are generated by replaying the recorded true-state trajectory, **offline**, so the label code can be revised without re-running flights (must be deterministic and versioned via `label_version`).

### 6.4 Oracle hierarchy for baselines (for agent 05)

`Oracle-0` (L = 1 tick, perfect state), `Oracle-L` (same with injected latency L) = the `F_B(L)` reference; random and always-HOVER controls; `rollout-labeller` = the label generator above. Near-zero cost (point-mass) so labelling 10^5 decisions takes seconds.

## 8. Contradictions / cautions relative to `docs/initial-plan.txt`

- The plan implies a low-latency reactor shows a dramatic advantage ("killer demo"). The math says the advantage exists **only for scenarios with budget between the two reactors' latencies** (tier T2-T4 for Jev vs LLM) and is **bounded by physics floor** `v tau_a + v^2/2a`; below that, nothing helps. A demo constructed at budget ~0.5 s with a 2 s LLM is honest; a demo at budget < 10 ms is not (even oracle fails).
- CF2X is a 27 g drone with default speed cap 0.25 m/s in the fetched `VelocityAviary` source [V]; the plan's "drone avoids an obstacle that appears unexpectedly" at these speeds is trivially avoidable (B ~ seconds) unless speeds/ranges are scaled. Decision needed on scaling.
- "Wind changes, battery drops, GPS disappears" are **not native** to gym-pybullet-drones (only ground effect/drag/downwash as optional modes [V from URDF coefficients; README to be confirmed by 02]); all seven events need custom code, of which obstacle/intruder/target are trivial kinematics, wind is a per-step `applyExternalForce`, battery is an rpm scale, and GPS/sensor faults are observation-layer only unless an estimator stub is added.
- Most events (wind, sensor noise, battery, GPS) have no *discrete* "correct action" at the instant of onset; they are stressors. Only obstacle/intruder/battery-critical/GPS-loss produce hard deadlines. Any claim about "reacting to all 7 events" must reflect that asymmetry.

## Decisions recommended

1. Adopt **reaction budget `B = (d - d_min0)/v_c`** as the canonical difficulty measure; generate scenarios budget-first (`d = d_min0 + v_c (B + t_det)`); tiers T0-T5 plus an impossible control tier T-1 (excluded from headline rates but always reported).
2. Sample the headline suite with `B ~ LogUniform(10 ms, 5 s)`, plus a stratified equal-N-per-tier suite for power; predict `P(collision) = CDF_B(L_eff)` and plot outcomes vs `rho = L_eff / B`.
3. **Calibrate `a_brake`, `a_lat`, `tau_a` empirically** in the real PID+sim (section 3.6), apply `kappa_a = 0.85` and +0.10 m, and **certify every scenario** with a 1-tick Oracle-0 replay in the simulator (reject and resample otherwise).
4. Use **range-triggered, world-fixed spawns**; cap all arms at `v_cap` (2 m/s default, closing speeds 0.5..5 m/s), report realised budget per flight.
5. Wind = mean step + OU turbulence (Dryden-inspired, `tau = L/max(V,1)`), via per-step `applyExternalForce`, severity capped so `a_w <= 0.5 a_brake` (w <= ~5.4 m/s for CF2X). Battery = rpm scaling by `V/V_ref`. Sensor faults and GPS loss in the observation layer for v1; estimator stub only later.
6. Obstacles and intruders are pre-created parked kinematic (mass 0) bodies teleported into place; intruder is scripted and non-adaptive in certified tiers; adaptive adversaries go in a separate uncertified "stress" class.
7. Randomness via per-channel Philox streams pre-generated by step index (arm-independent); scenario_id = hash of canonical JSON; pydantic v2 models define the schema.
8. Ground truth = **viability-set labels** from point-mass rollouts (`S(t)`, `preferred`, `deadline`), stored both at observation-time and apply-time, computed offline and versioned (`label_version`). Include decoys and ghosts for false-alarm measurement.
9. Treat wind, noise, GPS (unflagged), target moves as stressors/traps; do not claim discrete-reaction results for them.
